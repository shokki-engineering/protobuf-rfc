## Services

### Packs

Packs manages SenML Packs, RFC 8428 <https://www.rfc-editor.org/rfc/rfc8428.html>.  A pack is stored as it arrived, base fields and relative times intact, and is served the same way. Resolution (section 4.6 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.6>) is a method here rather than something Create does on the way in, because it is lossy in one direction that matters: a relative time resolved on arrival records when the server received the pack, which section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> warns can be minutes out from when the reading was taken. Storing the pack unresolved keeps that decision with the caller who knows the answer.  The four wire encodings -- senml+json, senml+cbor, senml+xml and senml-exi, section 12.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-12.3> -- are not methods here. They are codecs registered against "protobufrfc.dev/Pack" and moved by `protobuf.shared.interchange.v1.Interchange`, so a new encoding is a codec registration rather than a change to this service.  **Whole packs only.** Reading and writing *parts* of a pack is RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html>'s FETCH and PATCH, and lives next door in `PackRecords`. The split is rule 2's -- one `service` block cannot span files and neither service fits in 250 lines with the other -- but it lands on a real seam: this service treats a pack as one document, and that one addresses the records inside it.

### PackRecords

PackRecords reads and writes parts of a pack, RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html>.  RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html> defines FETCH, PATCH and iPATCH over SenML for CoAP, where the point is not spending a constrained radio link on a whole pack to read one reading out of it. The same argument holds over HTTP once a pack has thousands of records, so the operations are here rather than left at the CoAP edge.  **A second service on the same resource, not a second resource.** Rule 2 forces it: one `service` block cannot span files, and `Packs` plus these two methods will not fit in 250 lines. The seam is real -- `Packs` treats a pack as one document, this addresses the records inside one -- but nothing here owns anything. Both services operate on "protobufrfc.dev/Pack" and a caller may use either at any time.  **Why not `UpdatePack` with a field mask.** A mask names *fields*, and every record lives in one repeated field, so the finest a mask can go is "replace all records". RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html> selects by content instead -- by name, and optionally time and unit -- which is a different addressing scheme, not a finer one. The two coexist: use `UpdatePack` to replace a pack, this to edit inside it.  **Neither method is called what the RFC calls it.** AIP-131 <https://aip.dev/131> reserves `Fetch` as a synonym for `Get` and AIP-134 <https://aip.dev/134> reserves `Patch` as a synonym for `Update`, and api-linter rejects both as method-name prefixes -- a method called `PatchPack` reads to a generated client as the standard update it is not. The verbs used instead are RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html>'s own: section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1> says FETCH is used "to select and return a subset of Records", and section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> speaks throughout of patch records being *applied*. The CoAP methods are named in each RPC's comment, and the table in `docs/conventions.md` records the rename.  Reference: RFC 8790 "FETCH and PATCH with Sensor Measurement Lists (SenML)". https://www.rfc-editor.org/rfc/rfc8790.html

### Pack

Pack is a SenML Pack: one or more SenML Records in an array, RFC 8428 section 4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4>.  The unit a sensor publishes and a consumer fetches. Section 12.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-12.3> registers four media types for it -- "application/senml+json", "application/senml+cbor", "application/senml+xml" and "application/senml-exi" -- which is the whole point of the format: one data model, four wire encodings, chosen by how constrained the device and the link are. The four are codecs registered against "protobufrfc.dev/Pack" in `shared/interchange/v1`, not four schemas.  A flat collection, "packs/{pack}". Section 4.7 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.7> is explicit that SenML carries the minimum dynamic information and that static metadata about the device or sensor is held **out of band**, by CoRE Link Format, so there is no device or sensor resource in this RFC to nest a pack under. Inventing one would assert a containment RFC 8428 <https://www.rfc-editor.org/rfc/rfc8428.html> deliberately declines to define -- the same reasoning that keeps `Resource` flat in rfc9073.  What identifies a sensor is instead a *string*: `base_sensor_id` and `sensor_id` concatenated, which section 4.5.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.1> requires to be globally unique and constrains to characters usable directly in a URI path. Filter on it with AIP-160 <https://aip.dev/160> rather than looking for a parent in the resource name.  Reference: RFC 8428 "Sensor Measurement Lists (SenML)", section 4. https://www.rfc-editor.org/rfc/rfc8428.html#section-4

Hoisting it is lossless in both directions and removes the one place the records could contradict each other. ### FetchRecord

FetchRecord selects records out of a pack, RFC 8790 section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>.  A cut-down `Record`: a name to match, optionally narrowed by a time and a unit. Section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1> is closed about the field list -- "Fetch Records MUST NOT contain other fields than name, base name, time, base time, unit, and base unit", and an implementation "MUST reject and generate an error" for a Fetch Pack carrying anything else. Those six fields are exactly what is here, so the schema enforces the rule by having nowhere to put a seventh.  **Not a `Record` with fields left unset**, and the difference is not cosmetic. Section 3 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3>: "the Fetch and Patch Records do not have a default time or base version when the fields are omitted." A `Record` with no time means time zero, which RFC 8428 section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> reads as "now"; a FetchRecord with no time means *match any time*. Reusing `Record` here would turn "give me every reading from this sensor" into "give me the one taken now", silently. That is why the two time fields carry explicit presence.  Matching is against the **resolved** form of both sides, section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>: base name concatenated onto name, base time added to time, so a fetch written with base fields matches a target written without them.  Reference: RFC 8790 "FETCH and PATCH with Sensor Measurement Lists (SenML)", section 3.1. https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1

| `base_time_value` | `double` | `OPTIONAL` | Base Time (bt). Added to `time_value` when narrowing by time.  Explicitly optional, unlike its counterpart on `Record`: absent here means "any time", not zero. See the message comment. |
| `time_value` | `double` | `OPTIONAL` | Time (t). When set, only a target record whose resolved time *and* name are equal is matched, section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>. Explicitly optional for the reason above. |
| `base_unit` | `string` | `OPTIONAL` | Base Unit (bu). Applies to this and following fetch records that set no `unit` of their own. |
| `unit` | `string` | `OPTIONAL` | Unit (u). When set, only a target record whose resolved unit and name are equal is matched, section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>. When both this and `time_value` are set, both must match. |

### PatchRecord

PatchRecord adds, replaces or removes one record of a pack, RFC 8790 section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2>.  It is a selector and a payload at once: the name, time and unit pick the target the same way a `FetchRecord` does, and everything else is what the target becomes. Three outcomes, all from section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2>: a match is replaced with this record's contents, no match means this record is added to the pack, and `remove` deletes the match.  Each patch record must match **at most one** target. Section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> calls a record matching several invalid, because applying one patch to many targets would leave the pack holding copies of the same record.  **Not a `Record` plus a flag.** The same presence problem `FetchRecord` has -- an absent time means "any", not zero -- plus one of its own: `Record` requires a value or a sum, and a removal carries neither. Section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> spells a removal `"v":null`, which protobuf has no way to express on a `double`, so the null becomes `remove` and the rules become this message's.  Reference: RFC 8790 "FETCH and PATCH with Sensor Measurement Lists (SenML)", section 3.2. https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `base_sensor_id` | `string` | `OPTIONAL` | Base Name (bn), matched as in a fetch record. |
| `sensor_id` | `string` | `OPTIONAL` | Name (n), matched as in a fetch record. A name matching nothing in the target pack adds the record rather than failing, section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2>. |
| `base_time_value` | `double` | `OPTIONAL` | Base Time (bt). Explicitly optional: absent means "any time", not zero. |
| `time_value` | `double` | `OPTIONAL` | Time (t). Explicitly optional, for the reason above. Section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> compares resolved times, and replaces the target only when the times either are equal or are absent on both sides. |
| `base_unit` | `string` | `OPTIONAL` | Base Unit (bu). |
| `unit` | `string` | `OPTIONAL` | Unit (u), compared like the time. |
| `base_value` | `double` | `OPTIONAL` | Base Value (bv), written onto the target. |
| `base_sum` | `double` | `OPTIONAL` | Base Sum (bs), written onto the target. |
| `sum` | `double` | `OPTIONAL` | Sum (s), written onto the target. Section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> accepts a sum in place of a value, matching RFC 8428 section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. |
| `update_duration` | `Duration` | `OPTIONAL` | Update Time (ut), written onto the target. |
| `number_value` | `double` | - | Value (v). |
| `string_value` | `string` | - | String Value (vs). |
| `boolean_value` | `bool` | - | Boolean Value (vb). |
| `data_value` | `bytes` | - | Data Value (vd), held decoded as everywhere else here. |
| `extensions` | `repeated ExtensionField` | `OPTIONAL` | Extension fields to write onto the target, RFC 8428 section 4.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.4>.  The must-understand rule does **not** apply in a patch. RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html> section 5 <https://www.rfc-editor.org/rfc/rfc8790.html#section-5> suspends it: an unrecognised label here "MUST NOT generate an error" and is written to the target like any other field, even spelled with the trailing "_" that would be fatal in a pack. |
| `remove` | `bool` | `OPTIONAL` | Delete the matched record instead of writing to it.  This is section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2>'s `"v":null`, which has no protobuf spelling: a `double` field cannot be null, and an unset one is indistinguishable from a patch that simply carries a sum instead. A named boolean says the same thing and cannot be misread.  A removal that matches nothing is not an error -- section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> says such a record "MUST NOT be added", so the outcome is simply no change. |

### SelectPackRecordsRequest

Request message for PackRecords.SelectPackRecords, RFC 8790 section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `name` | `string` | `REQUIRED` | Name of the pack to select from, "packs/{pack}". |
| `records` | `repeated FetchRecord` | `REQUIRED` | The selectors, in order. This is RFC 8790 <https://www.rfc-editor.org/rfc/rfc8790.html>'s Fetch Pack, and like any SenML pack its order matters: a base name or base time set in one fetch record applies to the records after it.  At least one, section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>: "A Fetch Pack MUST contain at least one Fetch Record." Capped at 1000, the ceiling used everywhere else here. |

### SelectPackRecordsResponse

Response message for PackRecords.SelectPackRecords, RFC 8790 section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `records` | `repeated Record` | - | The matched records, in the order the selectors asked for them.  Each target record appears **at most once**, section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1>, even when several fetch records match it. Deduplication is the server's job, not the caller's.  An empty list is a successful answer, not an error: section 3.1 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.1> says an unmatched fetch returns "an empty SenML Pack (i.e., array with no elements)". |

### ApplyPackPatchRequest

Request message for PackRecords.ApplyPackPatch, RFC 8790 section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2>.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `name` | `string` | `REQUIRED` | Name of the pack to patch, "packs/{pack}". |
| `records` | `repeated PatchRecord` | `REQUIRED` | The patch records, applied in this order.  Section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2>: "The Patch Records MUST be applied in the same sequence as they are in the Patch Pack", and concurrent patches must come out equivalent to some single sequence. Order is not a hint.  Capped at 1000 per call. A patch is all-or-nothing, so a request that has to be retried should be small enough to retry. |
| `etag` | `string` | `OPTIONAL` | Weak validator, AIP-154 <https://aip.dev/154>. When set, the patch succeeds only if the pack is unchanged since it was read.  Worth setting more often than on an append: a patch matches by name and time, so a record that arrived since the caller read the pack can turn a one-target match into a two-target one, which section 3.2 <https://www.rfc-editor.org/rfc/rfc8790.html#section-3.2> makes invalid. |

### Record

Record is one SenML Record: a single measurement or configuration instance in time, RFC 8428 section 4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4>.  A record carries two kinds of field. **Base fields** (section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>, the `base_` prefix here) apply to this record and to every record after it in the Pack, up to but not including the next record carrying that same base field. **Regular fields** (section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>) apply only to the record they appear in. Both kinds may appear in any record.  A record is therefore not self-describing: reading one in isolation gives the wrong sensor, the wrong time and possibly the wrong unit, because the base values that complete it live in an earlier sibling. Section 4.6 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.6> calls a record with the base values already folded in **resolved**, and `Packs.ResolvePack` is that operation.  One measurement per record, deliberately: section 4.5.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.4> says values measured together -- air pressure and altitude, latitude and longitude -- belong in separate records correlated by their time, not in one record with several values.  Reference: RFC 8428 "Sensor Measurement Lists (SenML)", section 4. https://www.rfc-editor.org/rfc/rfc8428.html#section-4

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `base_sensor_id` | `string` | `OPTIONAL` | Base Name (bn), section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>. Prepended to `sensor_id` in this and every following record, e.g. "urn:dev:ow:10e2073a01080063:".  Named base_sensor_id, not base_name: AIP-122 <https://aip.dev/122> bans the `_name` suffix on everything but display_name, given_name and family_name. `id` rather than `identifier` is AIP-140 <https://aip.dev/140>, and section 4.5.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.1> is explicit that the concatenation "must result in a globally unique identifier".  The character set is section 4.5.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.1>'s, which constrains the *concatenated* name: it must start with an alphanumeric and continue with "-", ":", ".", "/" and "_". Only the leading record of a run can be checked for that first character, so the rule is enforced here, on the field that begins the concatenation, and documented on `sensor_id`, which cannot see whether a base name precedes it. |
| `base_time_value` | `double` | `OPTIONAL` | Base Time (bt), section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>. Added to `time_value` in this and every following record. Seconds, with the two-regime reading described on `time_value`.  Named base_time_value, not base_time: AIP-142 <https://aip.dev/142> requires a `_time` field to be a google.protobuf.Timestamp, and this is a double that is only sometimes an absolute instant. The `_value` escape is the one `date_value` already took in rfc9553/card. |
| `base_unit` | `string` | `OPTIONAL` | Base Unit (bu), section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>. The unit assumed for this and every following record that carries no `unit` of its own, section 4.5.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.2>. |
| `base_value` | `double` | `OPTIONAL` | Base Value (bv), section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>. Added to `number_value` in this and every following record. Absent is zero, section 4.5.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.4>, so no explicit presence is needed here. |
| `base_sum` | `double` | `OPTIONAL` | Base Sum (bs), section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>. Added to `sum` in this and every following record.  Explicitly optional, unlike `base_value` above, because section 4.5.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.4> treats absence and zero differently here: a missing Base Sum next to a present Sum counts as zero, but a record with *neither* has no sum at all, and that is what decides whether section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2> still demands a value. |
| `sensor_id` | `string` | `OPTIONAL` | Name (n), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. Appended to the `base_sensor_id` in force, e.g. "voltage". Section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2> permits this to name a parameter or an actuator as well as a sensor; section 4.9 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.9> is the actuation case.  Named sensor_id, not name: a field called `name` makes api-linter treat the enclosing message as a resource, which `Record` is not -- the same rename vCard's N took to `name_components`.  The pattern here is section 4.5.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.1>'s continuation set, without the leading-alphanumeric rule: this field is usually a suffix, so "voltage" and ":current" are both legal halves of a legal whole. When no base name is in force it carries the whole name and must satisfy the leading rule too, which no per-field constraint can see -- a codec checks the concatenation. |
| `unit` | `string` | `OPTIONAL` | Unit (u), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>, e.g. "Cel", "%RH", "V". Falls back to the `base_unit` in force when unset, section 4.5.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.2>; having neither is allowed and leaves the unit to the application.  Free text, not an enum. Section 12.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-12.1> points at the IANA "SenML Units" registry, which RFC 8798 <https://www.rfc-editor.org/rfc/rfc8798.html> has already extended and which grows by expert review, so a closed list here would reject units registered after this schema shipped. Same call `Resource.resource_types` made in rfc9073. |
| `sum` | `double` | `OPTIONAL` | Sum (s), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. The integrated sum of the values over time, in `unit` multiplied by seconds. Named "sum" rather than "integral" for historical reasons, which section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2> notes itself.  Explicitly optional for the reason given on `base_sum`. |
| `time_value` | `double` | `OPTIONAL` | Time (t), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. When the value was recorded, added to the `base_time_value` in force.  Seconds, and read two ways depending on magnitude, section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3>: below 2**28 (268435456) it is relative to "now" -- zero meaning the sensor has no clock and the reading is roughly now, negative meaning seconds ago -- and at or above 2**28 it is absolute POSIX seconds since the Unix epoch, so the smallest absolute value expressible is 1978-07-04T21:24:16Z. Because base and regular are summed, a pair of relative values can drift over 2**28 and silently become absolute; section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> warns about exactly that.  Not a google.protobuf.Timestamp, and named `_value` rather than `_time` to keep AIP-142 <https://aip.dev/142> from demanding one: a relative time has no instant to put in a Timestamp until a reader supplies "now", and section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> leaves the accuracy of "now" to the surrounding system. Resolving to absolute time is `Packs.ResolvePack`'s job, and section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> expects it to happen before anything is archived. |
| `update_duration` | `Duration` | `OPTIONAL` | Update Time (ut), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. The longest a consumer should wait before this sensor provides a fresh reading; a longer silence means the sensor or the path to it has failed.  A google.protobuf.Duration, where every other time-ish field here is a double: section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2> defines this one as a period of seconds outright, with none of `time_value`'s relative-or-absolute ambiguity, and AIP-142 <https://aip.dev/142> requires a `_duration` field to be a Duration. |
| `number_value` | `double` | - | Value (v), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. Added to the `base_value` in force. |
| `string_value` | `string` | - | String Value (vs), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>, e.g. "Machine Room". |
| `boolean_value` | `bool` | - | Boolean Value (vb), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. |
| `data_value` | `bytes` | - | Data Value (vd), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. Arbitrary octets.  Held decoded. Section 4.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.3> carries this base64url-encoded without padding in JSON and XML and as a definite-length byte string in CBOR; a protobuf `bytes` field is already binary, so re-encoding it would store one of those two spellings and make the other lossy. Same treatment `StructuredData.binary` gives ENCODING=BASE64 in rfc9073. |
| `extensions` | `repeated ExtensionField` | `OPTIONAL` | Fields this schema does not model, section 4.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.4>.  SenML is extensible by design and section 4.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.4> *requires* a reader to ignore labels it does not recognise, so dropping them is non-conforming rather than merely lossy. Anything registered in the "SenML Labels" registry after this schema shipped arrives here and round-trips intact. |
