### Streams

Streams manages Sensor Streaming Measurement Lists, RFC 8428 section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8>.  The same surface `Packs` offers, plus an append: a stream grows after it is created, and section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8> ties each record's "now" to when that record was sent, so the order it grew in is part of the data.  The four sensml media types (section 12.3.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-12.3.2> onward) are codecs registered against "the-protobuf-project.org/Stream" in `shared/interchange/v1`, kept separate from the four senml types registered against "the-protobuf-project.org/Pack". A consumer asking for "application/sensml+json" is asking for stream semantics, and serving it a pack would answer a different question.

### Stream

Stream is a Sensor Streaming Measurement List, RFC 8428 section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8>.  The same records a Pack holds, collected over time instead of all at once. Section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8> registers four media types of its own for this -- "application/sensml+json", "application/sensml+cbor", "application/sensml+xml" and "application/sensml-exi", section 12.3.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-12.3.2> onward -- and requires a system using SenML this way to say so, because a consumer may read each record as it arrives rather than waiting for the whole thing to close.  **A separate resource from Pack, for one reason that is not cosmetic.** Section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8> resolves a relative time against when *that record* was sent, where a Pack resolves every relative time against when the pack was. A pack is one instant; a stream is one instant per record. Storing a stream as a Pack would collapse those into a single "now" and silently move every reading in it -- section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> puts that error at anything from a millisecond to a dozen minutes. `StreamRecord` is where the per-record instant lives, and it is the whole reason this package exists. ### StreamRecord

StreamRecord is one record of a stream together with the instant it was sent, RFC 8428 section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8>.  The pairing exists because section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8> says a relative time in a stream is read against "the time when the specific Record is sent in the stream". A `Record` alone cannot carry that: its own `time_value` is the offset being interpreted, not the instant to interpret it against.  A wrapper rather than a field added to the copied `Record`, so the copy stays byte-identical to `protobuf.rfc8428.pack.v1.Record` and the two cannot drift. The difference between a pack and a stream then lives in exactly one place -- here -- which is where section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8> puts it too.  Reference: RFC 8428 "Sensor Measurement Lists (SenML)", section 4.8. https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8

### Record

Record is one SenML Record: a single measurement or configuration instance in time, RFC 8428 section 4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4>.  A record carries two kinds of field. **Base fields** (section 4.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.1>, the `base_` prefix here) apply to this record and to every record after it in the Pack, up to but not including the next record carrying that same base field. **Regular fields** (section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>) apply only to the record they appear in. Both kinds may appear in any record.  A record is therefore not self-describing: reading one in isolation gives the wrong sensor, the wrong time and possibly the wrong unit, because the base values that complete it live in an earlier sibling. Section 4.6 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.6> calls a record with the base values already folded in **resolved**, and `Streams.ResolveStream` is that operation.  One measurement per record, deliberately: section 4.5.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.4> says values measured together -- air pressure and altitude, latitude and longitude -- belong in separate records correlated by their time, not in one record with several values. SenSML uses the same records as SenML -- section 4.8 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.8> changes only how they are delivered and how their relative times resolve -- so the two definitions must stay byte-identical apart from the package. Keep them in step when either changes.  Reference: RFC 8428 "Sensor Measurement Lists (SenML)", section 4. https://www.rfc-editor.org/rfc/rfc8428.html#section-4

| `unit` | `string` | `OPTIONAL` | Unit (u), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>, e.g. "Cel", "%RH", "V". Falls back to the `base_unit` in force when unset, section 4.5.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.2>; having neither is allowed and leaves the unit to the application.  Free text, not an enum. Section 12.1 <https://www.rfc-editor.org/rfc/rfc8428.html#section-12.1> points at the IANA "SenML Units" registry, which RFC 8798 <https://www.rfc-editor.org/rfc/rfc8798.html> has already extended and which grows by expert review, so a closed list here would reject units registered after this schema shipped. Same call `Resource.resource_types` made in rfc9073. |
| `sum` | `double` | `OPTIONAL` | Sum (s), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. The integrated sum of the values over time, in `unit` multiplied by seconds. Named "sum" rather than "integral" for historical reasons, which section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2> notes itself.  Explicitly optional for the reason given on `base_sum`. |
| `time_value` | `double` | `OPTIONAL` | Time (t), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. When the value was recorded, added to the `base_time_value` in force.  Seconds, and read two ways depending on magnitude, section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3>: below 2**28 (268435456) it is relative to "now" -- zero meaning the sensor has no clock and the reading is roughly now, negative meaning seconds ago -- and at or above 2**28 it is absolute POSIX seconds since the Unix epoch, so the smallest absolute value expressible is 1978-07-04T21:24:16Z. Because base and regular are summed, a pair of relative values can drift over 2**28 and silently become absolute; section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> warns about exactly that.  Not a google.protobuf.Timestamp, and named `_value` rather than `_time` to keep AIP-142 <https://aip.dev/142> from demanding one: a relative time has no instant to put in a Timestamp until a reader supplies "now", and section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> leaves the accuracy of "now" to the surrounding system. Resolving to absolute time is `Streams.ResolveStream`'s job, and section 4.5.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.5.3> expects it to happen before anything is archived. |
| `update_duration` | `Duration` | `OPTIONAL` | Update Time (ut), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. The longest a consumer should wait before this sensor provides a fresh reading; a longer silence means the sensor or the path to it has failed.  A google.protobuf.Duration, where every other time-ish field here is a double: section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2> defines this one as a period of seconds outright, with none of `time_value`'s relative-or-absolute ambiguity, and AIP-142 <https://aip.dev/142> requires a `_duration` field to be a Duration. |
| `number_value` | `double` | - | Value (v), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. Added to the `base_value` in force. |
| `string_value` | `string` | - | String Value (vs), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>, e.g. "Machine Room". |
| `boolean_value` | `bool` | - | Boolean Value (vb), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. |
| `data_value` | `bytes` | - | Data Value (vd), section 4.2 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.2>. Arbitrary octets.  Held decoded. Section 4.3 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.3> carries this base64url-encoded without padding in JSON and XML and as a definite-length byte string in CBOR; a protobuf `bytes` field is already binary, so re-encoding it would store one of those two spellings and make the other lossy. Same treatment `StructuredData.binary` gives ENCODING=BASE64 in rfc9073. |
| `extensions` | `repeated ExtensionField` | `OPTIONAL` | Fields this schema does not model, section 4.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.4>.  SenML is extensible by design and section 4.4 <https://www.rfc-editor.org/rfc/rfc8428.html#section-4.4> *requires* a reader to ignore labels it does not recognise, so dropping them is non-conforming rather than merely lossy. Anything registered in the "SenML Labels" registry after this schema shipped arrives here and round-trips intact. |
